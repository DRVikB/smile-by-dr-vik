# SmileCompose app audit — 1 October 2026

Scope: the committed app at `7d731df` (branch `release/v1-device-test`). Covered: generation paths, server and account security, privacy and on-device data, the Tooth Map and SlimSAM pipeline, Full-arch, iOS configuration, performance, dependencies, App Store readiness and the automated checks. Nothing was deployed and no live AI generation was run for this audit.

## Summary

The core is in good shape:
- **Automated checks:** 390 tests pass; TypeScript and ESLint are clean.
- **Generation endpoint:** requires sign-in, Pro, a reserved allowance, the AI-consent header and a size cap. Allowance is committed on success and refunded on failure; duplicates and rate limits are enforced in the database.
- **Code hygiene:** no secrets in the browser bundle (see finding 3), no stray logging, no `eval`, no TODOs.
- **iOS privacy configuration:** the privacy manifest, permission texts, export compliance, iCloud-backup exclusion, Keychain session and App Switcher cover all pass.

The findings below are ordered by priority. None is a data leak.

## Blockers for real-world use

1. **The deployed backend is out of date.** `smile-by-dr-vik.drvik.workers.dev` returns 404 for `/api/account/status` and `/api/case-library`. Sign-in, subscriptions, the cloud Case Library and live generation cannot work from the iOS app until the current Worker is deployed with the staging configuration (ENVIRONMENTS.md). Test mode works. *Needs the owner's go-ahead to deploy.*
2. **Legal documents have open items:**
   - `privacy.html`: 23 items (legal entity, contact, lawful bases, retention).
   - `terms.html`: 17 items.

   `npm run check:app-store` passes 28 of 33; the other 5 are these and the release keys (Supabase, RevenueCat `appl_` key). *Needs solicitor / DPO review; not something the code can resolve.*

## High

3. **`scripts/verify-production.mjs` fails on a correct configuration.** It treats every env variable named `*KEY*` as a secret, including the two keys that are public by design (`NEXT_PUBLIC_SUPABASE_ANON_KEY`, `NEXT_PUBLIC_REVENUECAT_IOS_API_KEY`), so `npm run check:production` fails. The Gemini key is not in the bundle. Fix: exclude `NEXT_PUBLIC_*` values from the secret list. This is a tooling bug, not a leak.
4. **SlimSAM and face detection run on the main thread.** ONNX Runtime runs in the page with one thread (no worker proxy). The ~5 s tooth refinement after a photo reaches the Studio can make taps unresponsive for that time. This is consistent with the delayed taps seen on the simulator after opening a case. Fix: run inference in a Web Worker (ONNX Runtime's proxy worker, or our own).
5. **SlimSAM runs on every Studio open**, even when nothing uses its result. Standard 4 / 6 / 8 / 10 and Full-arch generation no longer use per-tooth masks. Fix: keep the fast classical detection upfront, and refine with SlimSAM only when needed: one tooth selected, Custom picking, or Review tooth map. This saves ~5 s of CPU and battery per case.

## Medium

6. **The face model and its runtime download from third-party CDNs at run time** (`cdn.jsdelivr.net`, `storage.googleapis.com`), in the iOS app too. The photo never leaves the device, but first use needs a network connection, and it's an external dependency App Review may ask about. Fix: bundle them like SlimSAM (≈ 10–15 MB).
7. **Case data uses iOS's default file protection** ("until first unlock"), because it lives in the web view's storage. Only the photo picker's temporary files use complete protection. For clinical photos, consider the Data Protection entitlement set to Complete (a paid-team capability).
8. **The content policy restricts network connections only.** There is no `script-src`, so it gives little protection against injected scripts. Fix: add `script-src 'self' 'wasm-unsafe-eval'` plus a hash for the appearance boot script, then test the app, the MediaPipe runtime and ONNX Runtime.
9. **Dependency advisories** (`npm audit`):
   - `next` 16.2.0–16.3.5: critical, but in `next/og` ImageResponse, which this static-export app doesn't use. Patch update to 16.3.8 recommended.
   - `undici` (via wrangler) and `uuid` (via the Capacitor CLI): build tools only, not shipped.

## Low / polish

10. **The ••• menu on the photo screen stays open** until an item or the button is tapped again. Tapping elsewhere should close it.
11. **Some tap targets are under 44 pt:**
    - the Full-arch segmented controls (40 pt);
    - small template teeth (premolars) when picking on a phone. The review list and zoom are there as alternatives.
12. **Tooth Map quality on hard photos** (tested on six real clinical photos, not in git):
    - SlimSAM is clearly better on crowding and worn teeth.
    - It still includes a little of the lower incisors on one close-up.
    - On missing or gapped teeth it mostly falls back and flags "Check tooth".

    Expected for a general model; the review step remains the safeguard.
13. **Unused code paths kept behind switches:**
    - `PRECISION_FOR_MULTIPLE_TEETH` (multi-tooth compositing)
    - `FULL_ARCH_ARCH_COMPOSITE` (arch-level compositing for Full-arch)

    Both are off by design and tested. Remove them later if testing never calls for them.
14. **App size.** The debug build is ~91 MB, including SlimSAM (13 MB), ONNX Runtime (14 MB) and ~10 MB of large PNG demo/onboarding images. Converting those PNGs to JPEG/WebP would save several MB.

## Generation paths confirmed

- **Standard (4 / 6 / 8 / 10, multi-tooth, whitening, porcelain, composite):** the existing generator, with the lip and face lock and any painted area. There is no per-tooth compositing or mask guidance. One added prompt line keeps the facial identity, expression, lips, mouth width and opening, and head position.
- **Single tooth:** the Tooth Map mask for that tooth only. Shade uses the exact outline; shape changes use a small influence region that never reaches the gums. The result is composited onto the original and verified.
- **Full-arch:** the existing generator with the structured instruction (arch, restoration, shape, shade, texture, intensity, prosthetic gingiva), plus the lip and face lock. No segmentation.
- **Overlay:** display only. Fitted vector templates are never used for masks.

Not verified in this audit: a live generation on each path (the backend isn't deployed), and physical iPad landscape rotation (the simulator can't rotate).

## Recommended order

1. Fix the production-check false positive (finding 3). Minutes.
2. Move SlimSAM and face detection off the main thread, and refine only on demand (findings 4 and 5).
3. Patch-update Next.js (finding 9) and re-run the builds.
4. Owner actions: deploy the backend to staging, legal review, release keys (findings 1 and 2), then test the three paths live on the iPhone and iPad.
5. Bundle the face model (finding 6), tighten the content policy (finding 8), add data protection (finding 7).
6. Polish (findings 10, 11 and 14).
